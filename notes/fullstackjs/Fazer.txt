Ótima pergunta! Vamos destrinchar o funcionamento do middleware de erros e como o Error e o errorHandler estão conectados no Express.

1. Como o errorHandler é chamado?
No Express, sempre que você chama o método next() e passa um argumento (como um erro), o framework entende que houve um problema e direciona o fluxo para o middleware de tratamento de erros.

Por padrão, um middleware de tratamento de erros no Express é identificado porque aceita quatro argumentos: (err, req, res, next). Isso o diferencia de outros middlewares.

Exemplo no fluxo:
Você lança um erro com throw new Error("Mensagem de erro") ou passa um erro explícito para o next():

javascript
Copiar código
const checkLogin = async (req, res, next) => {
    const { mail, password } = req.body;

    try {
        const selectUser = await userLogin(mail, password);
        if (!selectUser) {
            const error = new Error("Usuário não foi encontrado.");
            error.status = 404; // Define o status HTTP
            throw error; // Lança o erro
        }
        res.send(selectUser);
    } catch (err) {
        next(err); // Envia o erro para o middleware de tratamento
    }
};
O erro lançado ou passado ao next() é automaticamente interceptado pelo errorHandler, que foi registrado como middleware.

2. De onde vem a new Error?
A new Error é uma classe embutida do JavaScript. Ela é usada para criar objetos de erro personalizados que podem ser lançados com throw. Quando você cria um erro com new Error("Mensagem"), o Express trata esse objeto como um erro padrão e redireciona para o middleware de tratamento de erros.

Exemplo de como funciona a classe Error:
javascript
Copiar código
const error = new Error("Algo deu errado!");
error.status = 500; // Podemos adicionar propriedades personalizadas
throw error; // Lança o erro
No caso do Express, ele detecta automaticamente esses erros e os direciona para o middleware de erros.

3. Como o errorHandler processa o erro?
Quando você registra o errorHandler com app.use(errorHandler), o Express chama essa função toda vez que um erro é lançado ou enviado ao next(err).

Ciclo de vida no Express:
Controlador ou Middleware: Um erro ocorre (lançado com throw ou enviado com next(err)).
Redirecionamento: O Express percebe o erro e pula todos os middlewares/rotas seguintes, direcionando o fluxo para o primeiro middleware de erro registrado (errorHandler).
Execução do Middleware: O errorHandler recebe o erro e responde adequadamente.
No seu caso, o errorHandler é assim:

javascript
Copiar código
function errorHandler(err, req, res, next) {
    console.error(err.stack); // Mostra o erro no console para debug
    res.status(err.status || 500).json({
        message: err.message || "Erro interno do servidor."
    });
}
err.stack: Mostra a pilha de chamadas para debug.
err.status || 500: Define o status HTTP (padrão 500).
err.message: Mostra a mensagem definida no new Error.

Ótima observação! Vamos esclarecer: onde usar o Error depende da responsabilidade de cada camada no seu projeto.

1. A responsabilidade de cada camada:
Controller:

Faz o papel de intermediar a requisição HTTP e a lógica de negócio.
Delega tarefas para o Service.
Decide como responder ao cliente (ex.: res.json()).
Lança erros específicos para o cliente.
Service:

Contém a lógica de negócio ou chamadas ao banco de dados.
Deve ser o mais "puro" possível: não interage com requisições HTTP diretamente.
Lança erros técnicos ou de regras de negócio.
2. Como os erros fluem entre Service e Controller?
Você pode usar Error em ambos os lugares, mas com propósitos diferentes:

No Service:
O Service lança erros quando algo dá errado na lógica ou no acesso ao banco de dados.
Exemplo: "Usuário não encontrado", "E-mail já registrado", "Falha no banco de dados".

No Controller:
O Controller recebe os erros do Service, ajusta o tipo da mensagem e o código de status HTTP, e depois lança o erro para o middleware de erro.
Exemplo: traduzir "Falha no banco de dados" em uma resposta genérica de "Erro interno do servidor" com código 500.

3. Exemplo prático com erros em ambos
Service (Erros de Lógica):
javascript
Copiar código
async function userLogin(userMail, userPassword) {
    const selectUser = await tableUsers.findOne({ where: { mail: userMail } });

    if (!selectUser) {
        // Lança um erro se o usuário não existir
        const error = new Error("Usuário não encontrado.");
        error.status = 404; // Status específico
        throw error;
    }

    // Validação de senha
    const isPasswordValid = bcrypt.compareSync(userPassword, selectUser.password);
    if (!isPasswordValid) {
        const error = new Error("Senha incorreta.");
        error.status = 401; // Status específico para autenticação
        throw error;
    }

    return selectUser; // Retorna usuário caso tudo esteja correto
}
Controller (Erros para o Cliente):
javascript
Copiar código
const checkLogin = async (req, res, next) => {
    const { mail, password } = req.body;

    try {
        // Chama o Service
        const selectUser = await userLogin(mail, password);
        res.send(selectUser); // Responde ao cliente se tudo der certo
    } catch (error) {
        // O Controller apenas encaminha o erro para o middleware de erro

    }

4. Por que separar os erros dessa forma?
Service:
O foco é validar e lançar erros baseados na lógica de negócio, sem se preocupar com o protocolo HTTP. Isso faz o código do Service mais reutilizável (ex.: usado em uma API ou CLI).

Controller:
O foco é adaptar as mensagens do Service para o cliente, usando códigos de status HTTP adequados.

5. Em resumo:
Use throw new Error no Service para lidar com problemas de lógica de negócio ou banco de dados.
No Controller, trate esses erros com try-catch e delegue ao middleware de erros usando next(error).
